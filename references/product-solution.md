# 产品方案与 Product Contract 参考

用于产品策略、功能方案、PRD、用户旅程、工作流、信息架构和交互设计。目标是让产品、设计、业务和工程不必自行发明关键产品行为。

## 目录

1. 产品问题框架
2. 产品系统，而非孤立页面
3. 产品规则

## 1. 产品问题框架

至少明确：

- **角色与情境**：谁在什么触发下使用；
- **期望进展**：用户真正想完成什么；
- **当前路径**：今天怎样做，摩擦、风险和有效部分分别是什么；
- **动因与证据**：沿用已定目标，对影响设计的各项假设记录对应行为和来源（见 [真需求参考](true-demand.md) 第 7 节）；
- **产品承诺**：新方案让用户获得什么可感知结果；
- **业务关系**：该行为如何支持业务目标，而不损害信任；
- **约束与非目标**：本阶段的设备、渠道、权限、市场、合规和范围边界。

先定义问题与承诺，再定义页面与功能。

## 2. 产品系统，而非孤立页面

从完整旅程检查：

1. 用户如何进入并理解当前状态；
2. 如何开始、暂停、返回或放弃；
3. 如何做关键选择并获得及时反馈；
4. 系统如何确认成功，用户如何验证结果；
5. 失败、冲突或中断后如何恢复；
6. 结果如何影响后续任务、其他角色和既有数据；
7. 重复使用时，系统如何减少认知和操作负担。

同时检查主路径与影子路径：后台动作、通知、权限、审计、跨角色交接、历史记录、撤销和回退。

## 3. 产品规则

关键规则使用单一权威表述；需要跨章节引用时使用稳定 ID，例如 `R-001`。

每条规则回答：

- 谁在什么前置条件下发起；
- 系统允许、阻止或自动执行什么；
- 对哪个对象和状态生效；
- 用户看到什么反馈；
- 数据或业务结果如何变化；
- 失败、重复、并发、取消或超时怎样处理；
- 是否可撤销，若不可撤销如何明确告知；
- 对其他角色、渠道和后续流程有何影响。

不要在多个章节用不同措辞重复同一规则。用 ID 引用原规则。

## 4. 交互与信息层级

在影响任务完成的关键界面按需检查：

- 用户应先看到什么，哪些信息可以延后；
- 用户此刻最重要的决定是什么；
- 内容能否扫描理解，而非必须逐字阅读；
- 主要操作是否符合熟悉的约定，是否需要额外解释；
- 次要信息和动作能否延后、折叠或删除；
- 文案是否使用真实业务词汇和现实内容；
- 危险、不可逆或高风险操作是否建立足够信任；
- 响应式、键盘、读屏、颜色对比和触控目标是否符合场景。

仅在视觉问题上使用视觉材料。流程选择、规则取舍和范围确认优先用文字。

## 5. 状态矩阵

不要只设计 happy path。按关键对象或步骤检查：

| 状态 | 要回答的问题 |
|---|---|
| 初始/未开始 | 用户如何理解价值并开始？ |
| 加载/处理中 | 进度、等待预期和可取消性是什么？ |
| 空状态 | 为什么为空，用户下一步能做什么？ |
| 成功 | 如何确认结果、查看影响并继续？ |
| 部分成功 | 哪些已完成、哪些未完成，能否重试？ |
| 失败 | 原因是否可理解，恢复动作是什么？ |
| 无权限/不可用 | 为什么受限，如何申请或返回？ |
| 超时/离线 | 是否保存进度，恢复后如何续接？ |
| 冲突/并发 | 哪个版本有效，如何避免覆盖？ |
| 重复/幂等 | 重复操作是否安全，用户看到什么？ |
| 取消/撤销 | 已产生的影响如何处理？ |

只保留与场景相关的状态，但不能因为界面稿未展示就忽略系统行为。

## 6. 验收示例

对条件性或高风险行为使用具体例子：

```text
Given [明确角色、对象状态和前置条件]
When [用户动作或系统事件]
Then [可观察结果、状态变化与反馈]
And [必要的下游影响或恢复能力]
```

示例用于消除歧义，不替代规则本身。覆盖正常、边界和至少一个失败/恢复场景。

## 7. 建议产物结构

1. **Summary**：1–3 句话，面向未来描述要做什么；
2. **Problem Frame**：现状、证据、问题与为何现在解决；
3. **Goals / Non-goals**：目标和明确边界；
4. **Actors / JTBD**：角色、情境和任务；
5. **Key Decisions**：重要选择及其来源，不重复规则；
6. **End-to-end Flow**：触发到结果及跨角色影响；
7. **Requirements**：带稳定 ID 的产品规则；
8. **Interaction & State Design**：层级、反馈和状态矩阵；
9. **Acceptance Examples**：关键条件行为；
10. **Success**：能反映用户任务完成的信号与必要护栏；若要据此判断经营效果，核对[业务方案](business-solution.md)第 2 节的指标口径；
11. **Dependencies / Assumptions / Risks**；
12. **Scope Boundaries / Outstanding Questions / Sources**。

对于小方案缩短结构，不用空章节占位。Summary 描述未来方案；Problem Frame 解释过去和现状，两者不要重复。

## 8. Ready for Planning 检查

- **Complete**：没有会迫使下游猜测的关键角色、规则、状态或异常；
- **Consistent**：术语、状态、规则和验收示例互相一致；
- **Focused**：一个连贯工作单元，没有混入独立成果；
- **Usable**：下游可以制定实现计划，而不需要发明产品行为；
- **Evidence-aware**：事实有来源，假设被标注，开放问题有所有者或决策点；
- **Reality-grounded**：需求来自具体场景和行为，不把功能请求或口头认可直接当作已验证需求；
- **No placeholders**：没有 `TBD`、假链接、伪数据或“后续再考虑”的关键空洞。

交接给工程时，把关键规则 ID 关联到正常与失败/恢复的验收示例。可自动化的例子可标注 `→ test`；只有实际运行过才报告测试结果。写清刚性业务行为以及留给工程的选择。用户已授权修订指定产物时直接修订；进入实现按该请求的授权范围处理。
