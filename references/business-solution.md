# 业务方案参考

用于业务模式、业务流程、运营机制、服务体系、增长路径、商业化、跨部门协同和新业务探索。不要机械填满所有章节；选择当前决策真正需要的部分。

## 目录

1. 业务诊断

## 1. 业务诊断

先把目标语言还原成问题语言：

- **决策者与结果承担者**：谁拥有决策，谁承担收益、成本和风险；
- **目标对象**：具体用户、客户、商户、员工、合作方或供给方；
- **待完成任务**：对象想取得什么进展，而非想要哪个功能；
- **需求证据**：真实案例、行为、数据、反馈、流失、延迟或人工补救；
- **动因与证据**：写明经营或战略目标，为影响决策的各项假设注明证据（见 [真需求参考](true-demand.md) 第 7 节）；
- **现状替代**：当前如何解决，哪些部分有效，为什么仍有缺口；
- **核心约束**：时间、预算、组织能力、合规、供给、渠道和系统边界；
- **反事实**：不行动的结果，以及方案不被采用时最可能的原因。

将事实、推断和假设分开。没有证据时写“尚未验证”，不要包装成结论。

## 2. 策略锚点

用与本次决定相关的条目说明业务策略：

1. **诊断**：最关键的问题与成因；
2. **指导选择**：解决问题的基本方法，以及明确不采用的方法；
3. **首要角色 / JTBD**：先服务谁，在什么场景完成什么进展；
4. **价值机制**：哪些动作、交换和反馈共同产生价值；
5. **成功指标**：选能识别价值是否产生的观察，必要时加上成本或质量护栏；
6. **工作主线**：交付或资源有实质依赖时再划分；
7. **非目标**：当前阶段主动不解决的事项。

避免以下伪策略：

- 用“提升体验、提高效率”代替具体诊断；
- 用功能清单代替指导选择；
- 同时服务过多首要人群；
- 只用曝光、注册、调用量等虚荣指标；
- 把工作主线写成互不相干的任务列表。

核对指标时，区分点击等动作与实际完成的任务。总量上升时一并看留存、质量或单位成本；若同期有其他变化，说明哪些结果还无法归因于本次试点。主指标可能伤害体验或信任时，选相应护栏。

## 3. 业务机制

按需检查下列结构是否闭环：

| 维度 | 关键问题 |
|---|---|
| 参与者 | 谁发起、供给、交付、审核、支付、支持和承担责任？ |
| 价值交换 | 每个参与者付出什么、得到什么，为什么愿意持续参与？ |
| 激励与约束 | 哪些激励会驱动正确行为，哪些规则防止套利或劣化？ |
| 获客与采用 | 目标对象如何知道、尝试、信任、切换并持续使用？ |
| 交付机制 | 从触发到履约的关键步骤、交接和服务标准是什么？ |
| 收入与成本 | 收益来源、主要成本、边际变化和规模瓶颈是什么？ |
| 数据与反馈 | 哪些信号用于判断质量、优化供需或控制风险？ |
| 治理与风险 | 权限、审计、合规、争议、例外和退出如何处理？ |

先判断是否存在彼此独立、参与价值相互依赖的用户群体，以及它们是否通过产品发生互动。例如，场地主通过平台提供时段、主办方在同一平台预订，双方的参与会影响对方的价值。店长与收银员在同一门店协作的 POS 流程应优先检查权限、交接与责任。确认具备平台机制后，再按需检查：

- **冷启动顺序**：先让哪一边有价值，初始供给或需求从哪里来；
- **跨边效应**：A 边增长是否真的吸引 B 边，还是只是假设会吸引；
- **同边竞争**：同一边的参与者之间是否存在稀释、挤出或质量劣化；
- **价值归属**：平台创造的价值中，各边实际感知到多少，是否有一边觉得被剥削；
- **多归属与锁定**：参与者是否同时使用竞品平台，切换成本是否足够；
- **平台中立性**：平台的运营规则和推荐机制是否会让某一边失去信任。

内部业务方案不一定需要收入模型，但仍需解释资源投入、运营负担和价值回收。

## 4. 端到端运营流程

从真实触发点画到结果闭环，而不是只画理想主路径：

`触发 → 识别/准入 → 匹配/决策 → 交付 → 确认 → 结算/记录 → 反馈/复用`

补齐：

- 各节点的责任角色、输入和输出；
- 人工与系统的边界；
- 等待、拒绝、取消、超时、重复、争议和补偿；
- 上下游交接、服务标准和升级路径；
- 质量控制、审计点和故障恢复；
- 试点阶段哪些动作可以人工完成，哪些必须产品化。

## 5. 方案选择

优先交代推荐的业务机制和失效条件。若谁付费、谁履约、如何分发或承担风险确实存在取舍，再并列比较。若差异只在实施规模，把它写成同一方案的试点和扩展条件。

## 6. 建议产物结构

1. 执行摘要与推荐；
2. 背景、诊断与证据；
3. 目标、非目标与成功指标；
4. 角色、JTBD 与现状替代；
5. 推荐业务机制与关键选择；
6. 价值链或端到端运营流程；
7. 业务规则、激励、治理与异常；
8. 产品或能力支撑；
9. 工作主线、阶段与试点学习闭环；
10. 风险、依赖、假设与回退；
11. 已确认决定和开放问题。

## 7. 完成检查

- 方案解释了“为什么会产生价值”，而不只是“要做什么”；
- 需求结论不只依赖口头认可；价值、共识与模式能在具体场景中形成闭环；
- 用户价值、业务价值和参与者激励没有互相冲突；
- 现状有效部分被明确保护；
- 主流程、影子流程和失败恢复都有人负责；
- 指标能证明问题被解决，而非只证明动作发生；
- 试点能验证核心假设，并定义继续、调整或停止的条件；
- 不在范围的事项不会让下游误以为被遗漏。
